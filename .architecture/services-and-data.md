# Genesis services and application data

This is the platform transport/data boundary. Applet authors use the portable [factory services guide](../factory/guides/services-and-data.md). HN record shapes and operations belong to the [HN reference applet](hacker-news.md), not the Genesis service API.

## Implemented capability

A manifest may declare services as unique logical identifiers and the services capability. Only the API-3 foreground context exposes services.request(serviceId, {path, method, body}). The result is {status, body}; the applet interprets HTTP status and application JSON. The host does not interpret HN collections or server operations.

Rust validates foreground role, declared service membership, allowed methods, relative path shape and live document/channel/generation binding. Hidden source adapters and website readers cannot use this broker. It emits ServiceRequest containing host-assigned applet and document identity. Android ServiceClient resolves a connection scoped to applet ID and service ID. Requests run outside the UI thread. GET cannot carry a body. POST/PUT/PATCH/DELETE may carry JSON.

Creators provision development connections with `genesis-applet service` or the compatibility wrapper `tools/services.mjs` and the applet-owned backend/service.json declaration. The tool starts HTTPS, checks authenticated health, creates adb reverse, and sends a one-time private debug import. The host validates declared membership and encrypts the token. Manual Service connections remains a creator troubleshooting tool. The endpoint must be an HTTPS origin with no user info, path, query or fragment. A changed origin requires a new token. Tokens are encrypted with an Android Keystore AES-GCM key before private SharedPreferences storage. JavaScript receives neither the stored token nor the key. Website cookies are not forwarded. Backend credentials are separate from website account sessions.

Transport constructs a path relative to the configured origin and rechecks scheme and authority. Redirects are disabled. TLS uses platform trust for ordinary endpoints. A debug-only imported certificate can establish trust for exactly that applet/service connection; hostname verification remains enabled. Release builds reject the private debug import. Responses and request bodies are capped at 256 KiB. Two network workers share a queue of 32 jobs per Activity. Connect and read timeouts are three seconds; response-body reading also checks a four-second elapsed deadline. These are bounded-operation safeguards, not a proven strict wall-clock deadline for every transport phase. Service workers stop accepting jobs on Activity destruction; an already submitted request can still reach its server.

Configuration edits affect future requests. Disconnecting removes saved configuration; it does not undo or guarantee cancellation of in-flight requests. Revocation-sensitive operations must also revoke the credential at the backend. Connection settings are scoped to the effective applet IDs; signed publisher/installation identity must be established before independent package installation.

The runtime allows multiple service IDs. The creator helper defaults to `backend/service.json`; `--service-file` selects another applet-contained declaration and starts one Node entrypoint per invocation, with private state scoped by applet/service ID. `--local` starts and health-checks a backend without a device. In the monorepo, operator-owned applet `start.sh` scripts and `factory/start-applet-servers.sh` run those services using reservations in `factory/ports.json`; agents maintain these without starting services unless explicitly asked. Device mode restores adb reverse and provisions connections. Provisioning restarts the debug host. Its ready receipt follows device-side health, but a failed health request does not roll back settings already committed. `status` checks the process rather than verifying end-to-end service readiness. Host service errors use generic wording. Applets supply domain-specific reader messages.

## Trust and application semantics

A configured backend is trusted to receive the chosen applet data and return data to that applet. This broker does not sandbox all outbound effects of DOM-capable code. An isolated world and Shadow DOM do not establish complete network confinement or protect users from a malicious customization with broad DOM access.

Servers enforce authentication and application authorization. The current HN process uses a single bearer token and a single database. It is a personal single-tenant backend, not a multi-user account service. Production deployment requires an operator-managed trusted HTTPS endpoint, durable volume, backups and appropriate network/rate controls. Server secrets stay outside source and frontend bundles.

Do not retry uncertain writes automatically. A transport or RPC timeout may happen after commit. Read current state before a user retries. HN still needs applet-owned idempotency keys and operation status for a stronger retry experience. The phase-4 X backend implements these in its own SQLite transactions, with operation receipts and revision preconditions; this does not create a generic host synchronization engine. Dropping a late UI completion does not roll back a remote write.

## Local storage and migration

Generic host SQLite remains available through the optional storage capability for other applets and future caches. It stores namespace-scoped JSON documents with revision-checked transactions. HN retains public preferences and legacy draft records in host storage; new original-site forms stay in the explicit provider and do not export fields through source models. X persists accepted account observations only from its foreground, bound to the current visit. Bookmarks and categories remain authoritative on the service. Existing files/genesis.sqlite3 is preserved. It is not silently copied or merged into the remote backend.

HN's explicit import tool accepts a consistent legacy database copy and an empty server database. It imports only profile local, applet hn-bookmarks, supported schema and HN collections, preserving keys, JSON, revisions and timestamps. A populated destination is refused. Stop the backend before import. This operator tool is not yet a user-facing export/migration workflow.

A bounded in-memory public HN page cache can retain last loaded content with a stale notice. Saved/category reads still require the backend, and there is no durable offline authority or offline write queue. An offline cache would live in the applet with explicit authority, conflict and sync behavior. It should not become a universal Rust synchronization policy.
