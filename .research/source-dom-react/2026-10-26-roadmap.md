# Genesis customization engineering roadmap

Current implementation sequence: [LIVE-01 through LIVE-07](../live-dom-customization/05-implementation-roadmap.md). The React/Kotlin phases below are historical alternatives, not additional prerequisites for the incremental-customization prototype.

Date: 26 October 2026, Asia/Kolkata. Proposed work only. No phase is implemented or accepted. [Research](2026-10-26-research.md) and [architecture](2026-10-26-architecture.md) supply rationale and contracts.

## Scope and decision order

Prove a local React interface driven by a live website before building a universal browser fork. YouTube's original-player path is an early feasibility gate. General automation, arbitrary generated native code, an Android replacement, marketplaces and unattended background work are outside this roadmap.

Use deliverable gates rather than promising a completion date. Time-box the first capability experiment to five engineer-days as a proposed spending limit; that is not a claim that all required experiments will pass in that time. If it does not settle a requirement, record the evidence and remaining work rather than marking the gate complete.

Implementation location and reuse of the existing Bonsai Android host should be decided before writing runtime code. This research does not move or modify that application. Code must follow the instructions applicable at implementation time.

## G0. Browser, observation and media feasibility

Dependencies: none.

Deliverables:

- Inventory the actual Android/WebView provider and supported injection, messaging and navigation features.
- Load an owned dynamic fixture and a public target page in the phone runtime.
- Run two minimal presentations: a separate React view and an injected owned root. No new custom reconciler.
- Test whether the source continues to produce correct observations while the custom frontend is visible.
- Select a card in a custom list and open the original watch page without losing the intended source session.
- On owned video content, evaluate same-document styling and movement if inline reuse is essential. Record the exact method. A public YouTube playback check remains separate evidence.

Gate: record supported features, actual source liveness, successful source-to-result updates and a workable player presentation. If arbitrary inline player relocation is required and neither prototype supports it, stop dependent integration work and open the narrow engine experiment in G7. Do not hide that failure behind original-page fallback.

## G1. Observation and protocol

Dependencies: G0's supported runtime.

Compare a small subtree observer against rrweb capture using the same fixture. Measure implementation effort, captured properties, node identity, update bytes, CPU time and resynchronization behavior. Choose one canonical capture format or an explicit adapter, rather than stacking several mirrors.

Deliver document/frame/source identity, a snapshot-and-patch contract, ordered updates, bounded queues and full resynchronization. Include source-root replacement and input-property cases. Add immutable store selectors for the frontend.

Gate: reconstruct expected observed content across 100 controlled update sequences. Deliberately omit or reorder updates; every resulting sequence mismatch must trigger resynchronization or a detected failure. Never accept a corrupt tree as current. This is an engineering acceptance target, not a statistical reliability claim.

## G2. Custom React frontend

Dependencies: G1.

Implement a small SDK on React useSyncExternalStore, compiled applet loading, source status and original-page handoff. Render three layouts over the same observation contract: list, grid and a substantially different organization such as grouped sections.

Keep source nodes outside the custom root's ownership. An injected-root variant excludes its own subtree from capture. If its mutation rate feeds back into source capture indefinitely, it fails this gate.

Gate: all three layouts work without changing the host or capture adapter. Stage a broken React revision and recover to a working revision or original source page. No model call is required to render or filter observed data.

## G3. Source interaction binding

Dependencies: G1 and G2.

Implement navigation and activation first. Resolve current references, verify expected record identity and observe outcomes. Distinguish confirmed, rejected, needs-user and uncertain results. Keep a single source writer.

Gate: run 100 controlled interactions with record reordering, node recycling, navigation and deletion inserted before dispatch. Zero wrong-record operations are acceptable. A detected stale target is a correct refusal, counted separately from successful completion. Do not expand into rich-text or arbitrary form control until basic source binding passes.

## G4. Useful YouTube applet and retained player

Dependencies: G0 media result and G3.

Qualify loaded source cards and a custom browsing layout against the actual mobile site. Check empty/loading states, route changes, pagination or virtualization and back navigation. State coverage explicitly. Do not assume a familiar desktop DOM or account behavior applies.

Deliver the selected original-player mode. Test playback, pause/resume, seek, captions where available, fullscreen, rotation, focus and return to the custom layout. Compare the same content and session in ordinary source mode and custom mode. Do not replace the actual player with cloned video markup.

Gate: every advertised player interaction works in 20 repeated source/custom transitions on each primary qualified provider/device configuration. Any observed failures must narrow the capability claim or block the integration. This sample does not establish production reliability.

## G5. Creator workflow and local packages

Dependencies: G2 and a functional G3 workflow; some work can proceed before G4 if it does not depend on media.

Deliver a starter React codebase, capability inspector, fixture data, build/import commands, error console, preview, atomic activation and rollback. Preserve editable source and lockfile alongside compiled assets. The phone uses accepted applets with the laptop disconnected.

Gate: five independent creators complete three specified customization tasks each. Pilot target: at least 12 of 15 functional outcomes without a platform maintainer editing the host. Report creation time, unsupported requests, retries, new site-binding work and interventions separately. Compilation success alone earns no functional credit.

If phone-only editing is an MVP requirement, add a dedicated subphase for editor, compiler, dependency resolution and persistent source storage. Otherwise laptop editing plus local import is the initial workflow, explicitly described as such.

## G6. Second source, lifecycle and resources

Dependencies: G3 and G5; media remains required for the YouTube claim.

Add one different source after it passes independently. Feed both into one React interface, with separate errors, ages and source identities. Fail either source without replacing the other's data. Persist definitions and applet state, recover source documents and invalidate stale references after process loss.

Measure 1, 2 and 4 active/retained source configurations on at least two physical devices. Include the custom frontend and renderer processes in the resource accounting. Compare cold, warm and retained startup. Test custom view visible, source visible, another app active, locked device and process death independently.

Gate: select and document a supported live-tab budget from measured resource behavior. No universal tab count or browser-equivalent performance is assumed.

## G7. Conditional engine work

Dependencies: a documented required capability that failed G0-G6.

Compare these responses in order:

1. Change the applet's supported capability or preserve the original view.
2. Test GeckoView if the blocker is a standard host-injection or messaging capability.
3. Prototype a Chromium embedder-level feature with unchanged source/result contracts.
4. Modify Blink layout/compositing only if the requirement explicitly needs independent visual placement of live nodes and no narrower route works.

For engine work, define the failing test before patching. A new hook must specify document/frame identity, node lifetime, input/focus routing and presentation ownership. Establish Linux builds, reproducible APKs and an upstream-update process before expanding the patch set.

Gate: the exact previously failing test passes, ordinary browsing still works, and the ongoing update cost is measured. A screenshot or a successful Chromium compilation is insufficient acceptance evidence.

## Initial measurement targets

All numbers below are proposed prototype targets. Change them after recording a baseline, with reasons. Publish sample sizes and raw results.

| Measurement | Initial target or method |
| --- | --- |
| Local custom-UI response | p95 at or below 100 ms for local transforms, excluding source/network work |
| Capture-to-view freshness | p95 at or below 250 ms under the declared fixture workload; also report capture scheduling delay separately |
| Frame timing | Compare missed frame deadlines in source/custom mode at the actual display refresh rate |
| Source callback/serialization work | Start with p95 below 4 ms per batch on the primary test device, then profile; do not export all computed styles each batch |
| Source work volume | Record bytes/update, updates/second, queue depth, resync count and CPU cost |
| Local behavior | Zero model calls for rendering, local sorting/filtering and ordinary component interaction |
| Memory | Total proportional set size across app and renderers, incremental cost per configuration and renderer-loss count |
| Browser fallback | Restore original source view without resetting its session when the source runtime remains healthy |
| Data correctness | Zero silently wrong targets or falsely complete datasets in controlled qualification |

Use at least 100 samples per exploratory p95 condition and repeat across sessions. A p95 estimate from a small run is unstable. Do not compare a retained custom layout with a cold original page and attribute the difference to rendering quality.

Useful arithmetic for planning: at 60 Hz, a display interval is about 16.7 ms. Sending a 250 KiB whole-page snapshot ten times per second produces about 2.44 MiB per second before extra copies. Local execution can therefore cause significant work without any additional server request. Neither value is a product measurement.

## Suggested source ownership

Proposed paths, not files created by this research:

```text
android-host/       Kotlin browser, source lifecycle and package activation
packages/protocol/ Source identities, snapshots, patches and command schemas
packages/capture/  Source observer and selected property capture
packages/store/    Immutable mirrors, projections and subscriptions
packages/react/    Creator hooks and supported UI helpers
packages/devtools/ Inspector, previews, error reporting and import tools
adapters/          Versioned site-specific selectors and semantic bindings
applets/           User-editable React source and compiled revisions
fixtures/          Owned dynamic pages, media and expected states
```

Reuse the existing Android host layout if it is chosen. Logical packages do not require separate repositories, services or a large monorepo framework.

## Completion evidence

The MVP is demonstrated by a creator changing a local React codebase, previewing and saving a new working interface, disconnecting authoring tools, reopening it, using real source interactions, and recovering from a bad frontend revision. YouTube support additionally requires the selected original-player gate. Multi-source support requires the separate partial-failure and resource gate.

No research document can supply the missing empirical results. The first funded implementation should produce G0's capability report and source/player evidence, not an extensive browser fork.
