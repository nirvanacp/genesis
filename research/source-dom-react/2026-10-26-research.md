# Source DOM and React projection

Research date: 26 October 2026, Asia/Kolkata.

Read next: [architecture and proposed contracts](2026-10-26-architecture.md), then [engineering roadmap](2026-10-26-roadmap.md). Earlier context: [24 October comparison](../customizable-browser-applets/2026-10-24-technical-analysis.md).

Status: source research and proposed engineering design. No Android build, browser experiment, YouTube integration, model call or benchmark was performed. The code examples in companion documents specify interfaces to implement. They are not existing libraries or tested application code. Existing Bonsai plans and application source remain unchanged.

## 1. Judgment

The proposed separation is useful: let the website keep running, observe its live document, and let a local React application choose the interface. A practical first implementation does not require a Chromium fork or a replacement for React reconciliation.

The central abstraction needs two additions. It must consume changes over time, and it must send interaction requests back to the source runtime. A DOM tree alone cannot preserve a website's running JavaScript, media pipeline or service state.

Use this conceptual model:

```text
source runtime -> observed tree and properties -> React projection -> custom interface
source runtime <- validated interaction requests <- custom-interface events
```

The arrows describe continuing communication. The browser remains responsible for executing website code and communicating with its servers. React remains responsible for reconciling the custom interface. Genesis supplies observation, source identity, synchronization, interaction mapping and authoring tools.

Recommendation: compare a separate React WebView with an early-injected React root in the original document. Start with two views for clear DOM ownership and multi-source composition, while testing original-player preservation immediately. Select a same-document presentation mode only if it proves materially better for the media workflow. Reserve a browser fork for an identified capability that those approaches cannot provide.

Do not accept the performance premise that local execution guarantees browser-equivalent experience. The original website still runs, and observation, serialization and another frontend add work. This is an engineering inference from the additional components, not a measured slowdown. Ordinary-browser fallback must be designed and measured separately.

## 2. Correct the mental model

| Term | Meaning in an implementable system |
| --- | --- |
| Source runtime | The live website document, JavaScript environment, frames, media, storage and network activity |
| Source DOM | The actual document nodes managed by the website; useful input but incomplete application state |
| Source mirror | A bounded representation of observed nodes, selected properties and source references |
| React application | User-authored components and local UI state, compiled to browser-executable JavaScript |
| Result DOM | Nodes owned by the user's React application, in its own root or document |
| Live source view | The original browser view shown for interactions whose live state cannot be reproduced in the Result DOM |

Calling the source DOM the "True DOM" does not make it the service's database or the full state of its application. Virtualized lists, source-script state, canvases, media buffers and cross-origin documents require separate treatment.

React already converts component output into DOM updates. Its public createRoot API makes React responsible for the contents of its root. Its useSyncExternalStore hook provides a supported subscription mechanism for an external snapshot store. Reuse these instead of building another virtual-DOM reconciler. [React roots](https://react.dev/reference/react-dom/client/createRoot), [external stores](https://react.dev/reference/react/useSyncExternalStore).

The user-facing function can still look simple, but its inputs must be specified:

```text
result at time t = React(source snapshot at t, local UI state, resource handles)
source at next time = website runtime processing browser inputs and service responses
```

In a separate WebView, the Source DOM cannot be passed as a live ordinary JavaScript object. Send a serialized tree or selected records plus source-scoped references. Cross-environment serialization is a defined operation, not automatic sharing of DOM objects. [HTML structured-data model](https://html.spec.whatwg.org/multipage/structured-data.html).

### What a tree transformation preserves

| Source feature | Can a mirror represent it? | Does that preserve live behavior? |
| --- | --- | --- |
| Text, selected attributes and structure | Yes | Only their observed values |
| Current input value and checked state | Yes, if explicitly captured | Input events, validation and composition still need handling |
| Original event listeners and closures | Their effects may be observable | No, copying markup does not transfer the original execution environment |
| Loaded list records | Yes | Does not establish completeness of unloaded records |
| Computed appearance | Some styles and geometry can be captured | Does not produce a free arbitrary relayout or preserve pseudo-element behavior automatically |
| Video/canvas/complex editor | Metadata or snapshots can be represented | Keep the live source where execution state matters |

The DOM standard defines mutation observation, but an attribute/tree observer is not a subscription to every JavaScript property, CSSOM change or rendered pixel. Explicit input/property capture and selected media events are additional components. [DOM standard](https://dom.spec.whatwg.org/).

## 3. Architectural alternatives

### A. Two browser documents with a source mirror

One app-owned WebView runs the source website. A second hosts the local React applet. Source scripts send snapshots and patches through the Android host. Result interactions request work in the source.

Advantages: clean React ownership, source navigation does not destroy the custom frontend, and several sources can feed one interface. User React code does not have to manipulate the website's nodes.

Costs: a second frontend runtime, serialization, explicit resource handling and source-liveness management. A hidden source cannot be assumed to keep loading content or playing media as it did when visible. "Offscreen inside a foreground app" is different from "Android app in the background."

Suppressing source paint is also different from suppressing source layout. Websites can observe element geometry and intersection with a viewport. Removing layout with display:none or changing the viewport can therefore change what the website loads or how it behaves. A fork that skips original painting still needs to preserve the source geometry required by its code. [Intersection Observer specification](https://www.w3.org/TR/intersection-observer/), [CSSOM View geometry](https://www.w3.org/TR/cssom-view-1/#dom-element-getboundingclientrect).

Recommendation: baseline for content-driven applets. Retain an explicit live-source presentation path.

### B. Early-injected React root in the source document

Install the observer and presentation controller before ordinary app initialization where the platform permits. Mount React into a Genesis-owned element, possibly inside a ShadowRoot. Read the source subtree and show a custom interface while leaving the source runtime present.

This is more powerful than a post-load CSS patch. The runtime can observe, compute and render arbitrary React UI. It still shares a document and potentially a main thread with the website.

Advantages: potentially lower transport cost and more options to preserve existing live elements. Costs: styles, focus, full-screen elements, dialogs and source navigation can interfere. The page may remove the root or react to geometry changes. Exclude Genesis-owned nodes from source observation to prevent an update loop.

Do not mount React on the website's existing application root. React explicitly warns that arbitrary mutation of nodes managed by another React application can cause inconsistent results or crashes. Shadow DOM reduces some style collisions; it does not solve all global events, inheritance, layout or ownership issues. [React DOM ownership guidance](https://react.dev/learn/manipulating-the-dom-with-refs).

Recommendation: run a narrow media/layout experiment alongside A. Avoid supporting both full runtimes before comparing them.

### C. Move and restyle live source nodes

Reuse actual elements, CSS layout and selected node movement. This can retain behavior better than rebuilding everything from a snapshot, but it changes the DOM seen by the original website.

Chrome documents moveBefore as a state-preserving move operation. Its constraints include moving within the same document, with compatible connectedness. It cannot teleport a YouTube player into another WebView. It also does not guarantee compatibility with the website framework, ancestor-sensitive CSS or delegated events. Feature-detect and test it. [Chrome explanation](https://developer.chrome.com/blog/movebefore-api), [operation constraints](https://developer.mozilla.org/en-US/docs/Web/API/Element/moveBefore).

Recommendation: selective optimization for a known site component, not the universal foundation. Do not assume every ordinary node move necessarily destroys video state; that depends on the element and operation. The required evidence is uninterrupted behavior in the actual layout and provider.

### D. Fork Chromium and add a second presentation system

A fork can add native observation, richer frame access, custom input routing or presentation hooks. It does not turn the entire problem into a single DOM replacement.

Chromium rendering has style, layout, paint and compositing stages. It maintains frame, layout-fragment and property trees in addition to the DOM. Hit testing and input routing also use rendering structures. [RenderingNG architecture](https://developer.chrome.com/docs/chromium/renderingng-architecture), [data structures](https://developer.chrome.com/docs/chromium/renderingng-data-structures).

A fork that gives an original node an independent visual location must decide which geometry source scripts observe, where pointer events go, how focus/selection work, which accessibility tree is exposed and how embedded media is composed. A DOM-to-React function does not answer these questions.

If a fork becomes necessary, first add narrow host capabilities around the existing source/result contract. Avoid changing Blink's document and layout semantics until an experiment demonstrates that narrower hooks cannot satisfy the requirement. Relevant areas include content for document/embedder integration, Blink core for DOM/layout, cc and Viz for composition, and input/accessibility integration. Exact patch locations require a separate source-level spike. [Chromium layout](https://www.chromium.org/developers/how-tos/getting-around-the-chrome-source-code/), [cc responsibilities](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/how_cc_works.md).

Building Android Chromium currently requires an x86-64 Linux environment, at least 8 GB RAM and 100 GB free space; the official instructions recommend more than 16 GB RAM. These are documented build prerequisites, not a reliable development-machine budget or time estimate. [Android build instructions](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/android_build_instructions.md).

A custom system WebView provider is also not an ordinary drop-in library for every phone. Chromium documents predetermined provider package names. A forked browser APK and a replacement system WebView are different distribution designs. [WebView build instructions](https://chromium.googlesource.com/chromium/src/+/HEAD/android_webview/docs/build-instructions.md).

### Comparative judgments

Scores are ordinal judgments, not benchmarks. Freedom measures the custom frontend; compatibility measures how much original behavior remains directly available; engineering burden includes runtime integration. Higher means more of the named property. Do not sum them.

| Approach | Frontend freedom | Direct original-behavior reuse | Initial engineering burden |
| --- | ---: | ---: | ---: |
| A. Separate React document | 5 | 2 | 3 |
| B. Injected owned React root | 5 | 3 | 3 |
| C. Live-node rearrangement | 3 | 4 | 3 |
| D. New engine presentation system | 5 | Unproven | 5 |

These scores cannot establish memory use or universal compatibility. A and B have different failure modes despite similar scores. Original-view handoff increases usable coverage without establishing arbitrary inline rearrangement.

## 4. What existing software actually solves

| Software | Reuse | What Genesis still needs |
| --- | --- | --- |
| Android WebView and AndroidX WebKit | Browser execution, host integration, injection and messaging | Applet protocol, source mirror, actions and presentation ownership |
| React and React DOM | Components, reconciliation and frontend rendering | External-store adapter and source bindings |
| Vite | Compile and package local React projects for the browser | Applet manifest, install/update protocol and compatibility checks |
| esbuild / esbuild-wasm | Optional compact build tool or later on-phone compilation experiment | Dependency resolution, virtual files and package workflow |
| rrweb-snapshot and rrweb record | Evaluate source serialization, node identity and mutation capture | Service semantics, interactions, resources and full recovery |
| rrdom | Optional in-memory tree and patching reference | App-specific query/subscription model and mobile validation |
| Shopify Remote DOM | Authored UI synchronization across JavaScript environments | Arbitrary-site observation and source action mapping |
| GeckoView | Alternative Android engine with built-in extensions and messaging | Product-specific projection system; engine migration qualification |
| CDP DOM/DOMSnapshot | Desktop diagnostics, node mirrors and richer inspection | Shipping phone executor independent of developer debugging |
| react-reconciler | Custom renderer only if a new rendering target is justified | Host implementation and unstable API maintenance |

rrweb is unusually close to the observation half of this project. Its snapshot package assigns node IDs and captures selected state. It deliberately replaces script tags during serialization. Rebuilding the snapshot therefore does not recreate the original website's application execution. The replay interaction toggle permits input on a replay; it does not implement semantic forwarding into the live source page. [Snapshot documentation](https://raw.githubusercontent.com/rrweb-io/rrweb/main/packages/rrweb-snapshot/README.md), [replay interaction](https://raw.githubusercontent.com/rrweb-io/rrweb/main/docs/recipes/interaction.md).

rrdom is explicitly a virtual-DOM library for applying replay mutations. It is a candidate for reuse or design reference, not evidence that a universal live website projection is solved. [rrdom documentation](https://raw.githubusercontent.com/rrweb-io/rrweb/main/packages/rrdom/README.md).

Remote DOM is relevant in the opposite direction: code authors a tree in one JavaScript environment and a receiver renders supported UI in another. Its observer/receiver mechanisms merit evaluation, but arbitrary third-party scripts do not become compatible remote components automatically. [Project documentation](https://raw.githubusercontent.com/Shopify/remote-dom/main/README.md), [core mechanisms](https://raw.githubusercontent.com/Shopify/remote-dom/main/packages/core/README.md).

The react-reconciler package describes itself as experimental with an API less stable than React DOM. Since Result DOM is already a standard React DOM target, a custom reconciler adds no demonstrated MVP benefit. [Maintainer README](https://raw.githubusercontent.com/facebook/react/main/packages/react-reconciler/README.md).

Minimal initial adoption: WebView, AndroidX, React/React DOM, Vite and a small SDK. Run an rrweb-versus-small-observer evaluation before choosing capture code. Keep Remote DOM, rrdom and a custom reconciler optional until their savings are demonstrated. Do not combine all three synchronization systems by default.

### Current Android capability finding

AndroidX documents getExecutionWorld, addJavaScriptOnEvent and a world-aware addWebMessageListener overload from version 1.16. They require JS_INJECTION_IN_FRAME_AND_WORLD runtime support. This supports observing and rendering without changing Chromium, subject to actual provider qualification. [WebViewCompat reference](https://developer.android.com/reference/androidx/webkit/WebViewCompat?authuser=09).

The official release page currently lists 1.18.0, dated 21 October 2026; 1.16 raised the library minimum SDK to 24. The previous Bonsai catalog inspection found 1.15.0. This research proposes deliberate version qualification and changes no dependencies. The earlier report's unresolved reference-fetch issue is resolved for these API names by this investigation. [WebKit releases](https://developer.android.com/jetpack/androidx/releases/webkit).

## 5. YouTube is the media qualification case

The easiest part is projecting loaded card titles, links and other fields that a qualified page adapter can observe. Actual selectors, private-account behavior and coverage must be measured on the chosen mobile page. This investigation did not inspect a logged-in YouTube session.

The hard part is the player. A media element can be connected to JavaScript-managed buffers and other runtime state. A new video element with copied attributes does not carry the original MediaSource pipeline. [Media Source Extensions](https://w3c.github.io/media-source/).

Test in this order:

1. Custom React browsing interface, original live watch page on selection. This proves customization without claiming an arbitrary inline player.
2. React around a retained live source player, using same-document styling or an actual source view region. Qualify captions, seek, fullscreen, rotation and return navigation. Rectangular clipping is not arbitrary DOM reflow.
3. Same-document state-preserving movement only if needed and supported. Reject it if the source framework or playback fails.
4. A separately scoped engine presentation experiment if inline relocation is essential and no standard approach works.

YouTube's official iframe API can embed and control a player. It is a possible alternative product boundary, but it is not the same authenticated source-tab runtime. Do not silently substitute it for the user's requirement. [YouTube player API](https://developers.google.com/youtube/iframe_api_reference).

No media extraction, replacement decoder or server API is required for the proposed MVP. Preserving the original player is the first strategy to test. Protected playback, codecs and account compatibility must be checked for the selected engine and content; this report does not claim that an open-source Chromium build includes every component of Chrome.

## 6. Findings that could change the recommendation

| Finding to test | Consequence if it fails |
| --- | --- |
| Source stays correct while the React interface is visible | Revise source presentation/liveness before building more UI |
| Required injection works on target provider | Narrow supported providers or compare GeckoView |
| Original-player mode meets the MVP | An arbitrary inline-player requirement becomes an explicit engine research project |
| Two different React layouts reuse one adapter | Improve the source contract before adding sites |
| Mutations produce bounded traffic and observer cost | Narrow observed subtree/properties before adding full mirroring |
| Commands target current source state | Fix generation and identity before claiming functional customization |
| Ordinary browsing is recoverable after applet failure | Add a source-owned fallback independent of custom React |

A Chromium fork is justified by a failing required capability with evidence, not by the general fact that source code can be changed. Controlling the engine permits more implementation choices; it does not supply missing product semantics or a performance floor.
